Summary
I inspected the existing Compose/Dockerfile/nginx/health/config setup first, then built a full k8s deployment under k8s/ that maps directly onto it with zero application code changes:

k8s/base/ — namespace, ConfigMap/Secret (mirroring the app's own *_env_var convention), a postgres StatefulSet with PVC, rag-api Deployment (probes, resource limits, rolling-update strategy, graceful termination, init container) + Service + HPA, frontend Deployment/Service, an ollama-host ExternalName Service reaching your native host Ollama, an Ingress, and NetworkPolicy — tied together with a kustomize overlay.
k8s/jobs/ — a one-shot schema-init Job (mounts the real scripts/init_db.py via a generated ConfigMap).
k8s/observability/ — optional Prometheus/Grafana/Jaeger, reusing your existing observability/* config files unmodified.
k8s/README.md — full setup walkthrough (kind, image build/load, metrics-server, ingress-nginx, Calico caveat).
k8s/EXERCISES.md — the requested failure-injection walkthroughs (pod delete, scale, readiness failure, rolling update, bad image, node failure, NetworkPolicy, inspection toolkit).
k8s/LEARNING.md — text architecture diagram, a concept-by-concept "why," pod/node/rollout/HPA/traffic explanations, a section on what's genuinely process-local in this codebase and breaks under replication (the MCP in-memory case store is the real one), and 15 interview questions grounded in what's actually implemented.
A few honest findings worth knowing before you dive in: GET /health always returns HTTP 200 even when degraded (so readiness probes can't detect a downstream outage the naive way — documented and worked around in EXERCISES.md), kind's default CNI doesn't enforce NetworkPolicy, and kustomize's configMapGenerator load-restrictor rejected pulling files from outside k8s/ on the installed kubectl version — I used plain kubectl create configmap --from-file instead rather than fight it.
