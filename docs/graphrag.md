# Knowledge Graph and GraphRAG

A Neo4j property graph of entities and relationships (services, databases,
teams, policies, runbooks, incidents) derived from the document corpus, plus
a retrieval mode that combines graph traversal with vector retrieval.

The graph is additive. Dense and hybrid retrieval, RRF, reranking, relationship
expansion, authorization, freshness, trust filtering, and field redaction are
unchanged. `POST /query` and the agent's `classic_rag` route are not modified.
With `graph.enabled: false` (the default), no Neo4j driver is created and
ingestion writes no graph facts.

## Switches

| Setting | Default | Effect when off |
|---|---|---|
| `graph.enabled` | `false` | No Neo4j client is created. Graph extraction does not run. The graph agent tools are not offered to the model. |
| `graph.extraction.enabled` | `false` | Ingestion writes no graph facts. Graph retrieval can still read an existing graph. |
| `graph.extraction.llm_extraction_enabled` | `true` | When off, only deterministic facts are written. |
| `graph.cypher_generation.enabled` | `false` | Only the built-in query templates run. |
| `graph.fusion.strategy` | `vector_only` | Answers match plain vector retrieval. |

Graph capability is reached through the four agent tools
(`search_knowledge_graph`, `get_entity`, `get_neighbors`,
`find_dependency_path`) and through `POST /graph/query`, which returns 404 when
the graph is disabled.

## Architecture

```
ingestion: loader -> chunker -> embedder -> Postgres commit
                                              |
                              graph extraction (after commit)
                       deterministic facts + optional LLM facts
                                              |
                       GraphWriter: idempotent MERGE writes
                                              |
                                           Neo4j
                                              |
query: GraphRetriever (intent, entity linking, bounded traversal)
       -> authorization re-check -> GraphFact -> SearchResult (origin="graph")
       -> GraphRAGPipeline (fusion strategy) -> answer
```

## Schema

Node labels are a closed set in `rag.graph.schema.ENTITY_TYPES`: `Document`,
`Category`, `Tenant`, `Service`, `System`, `Application`, `Database`, `API`,
`Team`, `Policy`, `Runbook`, `Incident`, `CustomerCase`, `Customer`,
`Environment`, `Technology`, `Role`. There is no `Person` label, because the
corpus names teams and roles, not individuals.

Relationship types are also a closed set: `DEPENDS_ON`, `RUNS_ON`,
`CONNECTS_TO`, `OWNED_BY`, `GOVERNED_BY`, `HAS_POLICY`, `HAS_RUNBOOK`,
`APPLIES_TO`, `AFFECTS`, `PART_OF`, `SUPERSEDES`, `REFERENCES`, `RELATED_TO`.

`Document` and `Category` nodes and the `PART_OF` and `SUPERSEDES` edges come
from document metadata. All other types come from LLM extraction only.

**Provenance.** Each node and relationship carries `source_document_id`,
`source_chunk_id`, `dataset_id`, `tenant_id`, `allowed_roles`, `trust_level`,
`extraction_method` (`deterministic` or `llm`), `confidence`,
`document_checksum`, and `extracted_at`. `GraphRelationship` requires a
provenance block, so no fact can be written without it.

**Canonical ids.** `canonical_entity_id` is built from entity type, dataset,
tenant bucket, and the lowercased, whitespace-normalized name. The same name in
two datasets or two tenants gives two nodes. `rag.graph.canonicalization` adds a
hand-written alias table, for example `Postgres` to `PostgreSQL`. It is
deliberately not fuzzy matching, because fuzzy matching can merge distinct
entities.

**Constraints and indexes** are generated by `rag.graph.constraints`: one
`canonical_id` uniqueness constraint per label, plus `dataset_id` and
`tenant_id` indexes per label. A full-text index on `name` is created, but no
query template uses it yet.

## Extraction

The stage runs after the Postgres commit, and a failure in it cannot fail or
roll back the ingestion.

- **Deterministic.** `extract_and_write_for_document` writes a `Document` node
  keyed on the Postgres `document_id`, a `Category` node with `PART_OF`, and a
  `SUPERSEDES` edge when `supersedes_source` resolves to another document in the
  dataset. Resolution uses the same path-suffix rule as `retrieval/freshness.py`.
- **LLM (optional).** One call per chunk to the `graph_extract_v1` prompt. The
  response must validate against `LLMExtractionResult`, which uses
  `extra="forbid"` and the same `Literal` type allowlists as the schema. A
  response with an unknown type fails validation as a whole. Relationships below
  `min_confidence` (default 0.5) are dropped. At most
  `max_relationships_per_chunk` are kept per chunk.

## Authorization

Graph authorization applies the same rule as the SQL predicate in
`vectorstore/pgvector.py`, and it is enforced twice:

1. **Cypher predicate** (`build_graph_authorization_predicate`), added to every
   template that takes an auth clause. A fact is visible when its `tenant_id` is
   NULL, when the caller's tenant matches, or when the caller holds a configured
   cross-tenant support role that is also listed in the fact's `allowed_roles`.
   When `allowed_roles` is set, the caller must hold one of them. Freshness
   exclusions and `require_trust_level` apply as well.
2. **Python re-check** (`is_fact_authorized`), applied to every returned node or
   relationship, regardless of what the query's own `WHERE` clause did. This is
   the real boundary for LLM-generated Cypher.

A path is returned only when every node on it is authorized. A single
unauthorized hop removes the whole path.

3. **Postgres revalidation** (`rag.graph.fusion.graph_facts_to_search_results`).
   The Neo4j ACL is a copy written at ingestion time, so before a fact becomes
   evidence its source document is resolved in Postgres under the caller's
   resolved `AuthorizationContext`. A fact whose document was deleted, narrowed,
   or superseded is dropped, and the surviving fact carries the document's
   current tenant, roles, classification and trust. `graph_seeded_vector` filters
   its seed documents the same way.

Graph evidence then goes through `sanitize_evidence` like every other evidence
source, so field redaction and injection flagging apply to it too. Its
`sensitive_field_ids` are detected on the fact's own text, as for a chunk.

Tests that prove this include a live authorization scenario set in
`tests/integration/test_graph_authorization_isolation.py`.

## Retrieval

`GraphRetriever.search(query, dataset_id, auth)`:

1. **Intent** from literal keyword patterns: dependents, runbooks, owners,
   policy, impact, path, or entity lookup. It is not an LLM call, so the result
   is reproducible.
2. **Entity linking** from capitalized phrases in the query, resolved by exact,
   alias, or substring match within the dataset and the caller's authorization.
3. **Bounded traversal** through the template for that intent. Each template has
   an explicit depth bound and a `LIMIT`, and each query has a server-side
   transaction timeout.

On a Neo4j outage, `search` returns an empty result with `degraded=True`. It
does not raise.

**Templates** (`rag.graph.queries`): `dependents_of`, `runbooks_for`,
`owners_of`, `policies_governing`, `impact_of`, and `dependency_path`
(`shortestPath` with a depth bound).

**LLM-generated Cypher** is off by default. It is used only when no template
matches and entity linking finds nothing. `validate_generated_cypher` rejects
multiple statements, comments, write and admin keywords, `CALL`, unbounded or
over-deep variable-length patterns, and queries without `$dataset_id`. It
replaces any `LIMIT` with the configured maximum. This text check is
defense in depth only. The read-only transaction and the Python re-check are
the guarantees.

## Fusion strategies and agent integration

`GraphRAGPipeline` supports four strategies:

- `vector_only` (default): delegates unchanged to `RetrievalPipeline.answer()`.
- `graph_only`: answers from graph evidence alone.
- `vector_plus_graph`: graph facts are appended after the ranked vector results,
  never interleaved.
- `graph_seeded_vector`: entities are resolved first, and results from their
  linked documents are moved to the front. Nothing is removed.

Each strategy returns the same dict shape as `RetrievalPipeline.answer()`.

For `POST /graph/query`, the `strategy_used` field reports the requested or
configured strategy. It is not always the one that ran: a missing `dataset_id`
falls back to `vector_only`.

The four agent tools are offered only when `graph.enabled`. A graph-tool decision
made while the graph is disabled fails in `_execute_tool`, the same way a
disabled MCP tool does. If MCP client tools and graph tools are both enabled,
the MCP tool-selection prompt is used, and graph tools are not offered.

## Updates and failure behavior

- **Re-ingesting a changed document** runs `delete_facts_by_document` first. It
  deletes every relationship whose `source_document_id` matches, then deletes
  nodes first seen in that document that have no relationships left. A node
  still referenced by another document is kept.
- **Document removal** also deletes graph facts. Directory ingestion does this
  for documents it no longer finds, and `clear_dataset` does it for a whole
  dataset.
- **Postgres succeeds, Neo4j fails:** the failure is logged and counted. The
  document's graph facts are absent, and they are never half-written, because
  deletion runs before any new write.
- **Graph-only loss is not repaired by a plain re-run.** The checksum shortcut in
  `ingest_file` runs before graph extraction, and a Neo4j-only reset does not
  change the Postgres checksum. Recovery requires `IngestionPipeline.clear_dataset`
  or a real content change. Nothing reconciles the two stores automatically.
  `document_checksum` is stored on facts, but no code compares it.
- **Graph success with Postgres failure** cannot happen, because graph
  extraction only runs after the Postgres write commits.

| Failure | Behavior |
|---|---|
| Neo4j unreachable at query time | Empty result with `degraded=True`. The request is answered from the other evidence, or with the normal insufficient-evidence path. |
| Neo4j unreachable during ingestion | Graph extraction is skipped. Postgres ingestion is unaffected. |
| Query exceeds its timeout | Raised as `GraphUnavailableError`, which takes the degraded path. |
| Malformed LLM output | That chunk yields no facts, and the count is recorded. |
| Invalid generated Cypher | Rejected before it reaches Neo4j, and returns `unresolved`. |

## Observability and health

Metrics use bounded labels only: intent, strategy, and reason. They never
include node ids, names, or query text. There is a span per graph search. `GET
/health` reports `graph` as a soft dependency, which is always `True` when the
graph is disabled.

## Performance

Every query is bounded in depth and in rows. An unbounded variable-length
pattern visits a number of paths that grows exponentially with depth on a dense
graph, so bounds are required. The dataset and tenant indexes keep the starting
node lookup from scanning every label. No benchmark at scale has been recorded
(see Verification status).

## Demo dataset

`scripts/seed_graph_demo_data.py` ingests three real corpus documents and three
tracked synthetic documents from `data/graph_demo_docs/`. It then writes
hand-written relationships. Each one quotes or paraphrases a sentence from a
source document, and each is recorded with `extraction_method="deterministic"`.
One relationship, `RAG Service DEPENDS_ON Document Service`, is an inference. It
is marked as one in the script, and it gives the demo a two-hop chain.

With `--clear`, the seed script calls `clear_dataset` first, which resets the graph
and the Postgres chunks together. Without it, re-running adds to existing data.

## Running it

```bash
# Start Neo4j. This overlay is never started by plain `make up`.
make graph-up

# Create constraints and indexes. Safe to re-run.
python scripts/init_graph_db.py

# Enable the graph in a config. Copy config/default.yaml, then set
# graph.enabled: true, and graph.extraction.enabled: true to extract during
# ingestion. Use that file with --config and RAG_CONFIG_PATH below.

# Seed the demo dataset (optional).
python scripts/seed_graph_demo_data.py --config <your-config.yaml> --clear

# Query the graph through the API (requires the API to load that config).
curl -X POST http://localhost:8000/graph/query -H "Content-Type: application/json" \
  -d '{"query": "What depends on PostgreSQL?", "filters": {"dataset_id": "techfusion_graph_demo"}, "strategy": "graph_only"}'

# Compare fusion strategies on the graph gold set.
python -m rag.eval.run_graph_eval --gold data/eval/graph_gold.jsonl \
  --dataset-id techfusion_graph_demo \
  --strategies vector_only,graph_only,vector_plus_graph,graph_seeded_vector \
  --config <your-config.yaml>

make graph-down   # stop Neo4j
```

## Example Cypher

```cypher
// What depends on a service, bounded to 3 hops.
MATCH (target {canonical_id: $entity_id, dataset_id: $dataset_id})
MATCH path = (dependent)-[:DEPENDS_ON|RUNS_ON|CONNECTS_TO*1..3]->(target)
WHERE dependent.tenant_id IS NULL OR dependent.tenant_id = $_auth_tenant_id
WITH dependent, min(length(path)) AS hops
RETURN dependent, hops
ORDER BY hops ASC, dependent.name ASC
LIMIT $limit;

// Remove a document's facts before re-extraction.
MATCH ()-[r]->() WHERE r.source_document_id = $document_id DELETE r;
MATCH (n) WHERE n.first_seen_document_id = $document_id AND NOT (n)--() DETACH DELETE n;
```

The authorization clause is abbreviated here. The full predicate is built by
`build_graph_authorization_predicate`.

## When a graph helps

- **Vector retrieval is enough** for questions answered by one passage, such
  as "explain X" or "what does the policy say about Y".
- **A graph helps** when the answer composes facts from several documents,
  for example "what is impacted if this database fails", where no single chunk
  states the chain.
- **A graph adds cost without benefit** when the corpus has few
  cross-document relationships, or when those relationships are already stated
  in prose where they are needed.

## Concepts

1. **Knowledge graph.** Nodes are entities, edges are typed relationships
   between them, and both can carry properties. This implementation is a
   Neo4j property graph of corpus-derived entities (`Service`, `Policy`,
   `Team`, and so on), built alongside, not instead of, the existing
   Postgres/pgvector store.
2. **Node vs. relationship vs. property.** A node is one entity instance, for
   example a `Service` node named `RAG Service`. A relationship is a typed,
   directed edge between two nodes, for example `DEPENDS_ON`. A property is a
   key/value attribute on either one, for example `tenant_id` or
   `confidence`. Every node and relationship here also carries the
   provenance properties described under Schema.
3. **Property graph.** A graph model where both nodes and edges can hold
   arbitrary properties, as opposed to RDF, which represents facts as
   subject-predicate-object triples and models most other detail as further
   triples. Neo4j is a property graph. The direct comparison against this
   project's own RDF/ontology layer is in `docs/ontology.md`, section 9.
4. **Cypher.** Neo4j's declarative query language. Patterns read like ASCII
   art: `(a)-[:DEPENDS_ON]->(b)`. Every query in `rag.graph.queries` is a
   parameterized template, never built by concatenating caller input into a
   string.
5. **Graph traversal.** Following relationships outward from a starting node
   to discover connected nodes. Every template here bounds the traversal by
   hop count and `LIMIT` (see Retrieval above).
6. **GraphRAG.** Retrieval-augmented generation where some or all of the
   evidence handed to the LLM comes from graph traversal instead of, or
   alongside, vector similarity search. Implemented here as
   `GraphRAGPipeline`'s four fusion strategies.
7. **GraphRAG vs. vector RAG.** See Comparisons below.
8. **Multi-hop retrieval.** Answering a question that requires following
   more than one relationship, for example "what depends on what depends on
   X", where no single document states the whole chain. The
   `dependency_path` and `impact_of` templates are this implementation's
   multi-hop queries.
9. **Graph and vector hybrid retrieval.** `vector_plus_graph` and
   `graph_seeded_vector`, described under Fusion strategies above. Graph
   results are appended or used to reorder, never interleaved with a
   freshly computed score, so enabling fusion cannot silently change a
   result's relevance ranking in a way that is hard to explain.
10. **Knowledge graph vs. vector database.** See Comparisons below.
11. **Knowledge graph vs. ontology.** See Comparisons below, and
    `docs/ontology.md`.
12. **Entity resolution / canonicalization.** Deciding that two mentions,
    for example `Postgres` and `PostgreSQL`, refer to the same real-world
    entity. `canonical_entity_id` plus the hand-curated alias table in
    `rag.graph.canonicalization` does this deterministically. It is
    deliberately not fuzzy matching, because an incorrect merge of two
    distinct entities is worse than a missed match.
13. **Graph provenance.** Recording where a fact came from. Every node and
    relationship carries `source_document_id`, `source_chunk_id`,
    `extraction_method`, `confidence`, and `document_checksum`, so a fact
    traces back to a real sentence in a real document (see Provenance
    above, and the demo dataset's quoted-sentence discipline).
14. **Graph authorization.** Restricting which facts a caller may see by
    tenant and role, the same rule document-level ACL already uses,
    enforced twice: a Cypher predicate and a Python re-check (see
    Authorization above).
15. **Graph update consistency.** Keeping Neo4j in step with Postgres as
    documents are added, changed, or deleted (see Updates and failure
    behavior above, including the documented gap where a checksum shortcut
    can skip graph recovery).
16. **Why unbounded traversal is risky.** A variable-length pattern with no
    hop limit can visit a number of paths that grows with the branching
    factor raised to the power of the depth, exhausting memory or CPU on a
    dense graph. Every template here has an explicit depth bound, a
    `LIMIT`, and a server-side transaction timeout.
17. **Deterministic vs. LLM-generated Cypher.** Six hand-written,
    parameterized templates cover the supported intents reliably.
    LLM-generated Cypher is an optional fallback for an unmatched intent,
    off by default, and text-validated before it runs. The real guarantee
    is the read-only transaction mode plus the Python authorization
    re-check, not the text validator (see Retrieval above).
18. **When GraphRAG improves retrieval.** See When a graph helps, above.
19. **When GraphRAG adds unnecessary complexity.** See When a graph helps,
    above.
20. **How enterprise AI systems use semantic graphs.** Often as two layers
    together: a property graph, like this one, for fast traversal over
    specific entities, and an ontology/RDF layer for schema reasoning,
    standard vocabularies, and interoperability between systems that model
    the same domain differently. See `docs/ontology.md`, which is built on
    top of this same graph's data.

## Comparisons

**GraphRAG vs. vector RAG**

| | Vector RAG | GraphRAG |
|---|---|---|
| Retrieves | Chunks ranked by embedding similarity | Entities and relationships reached by traversal |
| Good at | A fact stated in one passage | A fact composed across several documents |
| Multi-hop | Only if one chunk happens to state the chain | Native; bounded by hop count |
| Cost | One embedding call, one search | Intent classification, entity linking, a bounded traversal |
| Failure mode here | Returns the nearest chunks even if irrelevant | Returns an empty, `degraded=True` result rather than a wrong traversal |

**Knowledge graph vs. vector database**

| | Vector database (pgvector here) | Knowledge graph (Neo4j here) |
|---|---|---|
| Unit of storage | A chunk and its embedding | An entity or a relationship |
| Query | Nearest neighbors by similarity | Pattern match and traversal |
| Answers well | "What text is most related to this query" | "What connects to what, and by what relationship" |
| Schema | Implicit, in the chunk's metadata columns | Explicit, a closed set of labels and relationship types |

**Knowledge graph vs. ontology.** A knowledge graph like this one stores
concrete instance facts: this `Service` node depends on that `Database`
node. An ontology describes the schema those facts conform to: what a
`Service` is, what `DEPENDS_ON` means, which classes are subclasses of
which. The two compose: `docs/ontology.md` builds an RDF/OWL ontology over
the same TechFusion domain and uses it to expand a query by subclass before
traversing this same graph. See that document's section 9 for the full
property-graph-vs-RDF comparison, including a case where RDFS closure alone
produced an incorrect inferred type and how SHACL caught it.

## Interview questions

1. **What is a knowledge graph?**
   A set of entities (nodes) and typed relationships (edges) between them,
   often with properties on both, used to represent and query how parts
   connect, not only what each part says in isolation.
2. **What is the difference between a node, a relationship, and a
   property?**
   A node is an entity instance. A relationship is a typed, directed edge
   between two nodes. A property is a key/value attribute on either one.
3. **What is a property graph, and how does it differ from RDF?**
   A property graph lets both nodes and edges carry arbitrary key/value
   properties directly. RDF represents every fact as a subject-predicate-
   object triple, so a property on a relationship becomes its own triple
   (often via reification) rather than an attribute on an edge.
4. **What is Cypher?**
   Neo4j's declarative graph query language. Patterns are written to look
   like the graph itself, for example `(a)-[:DEPENDS_ON]->(b)`.
5. **What is graph traversal, and why does it need to be bounded?**
   Following relationships outward from a node to reach connected nodes. An
   unbounded traversal on a dense graph can visit a number of paths that
   grows exponentially with depth, so every traversal here has an explicit
   hop limit and a result `LIMIT`.
6. **What is GraphRAG?**
   Retrieval-augmented generation where graph traversal supplies some or
   all of the evidence handed to the LLM, instead of or alongside vector
   similarity search.
7. **How does GraphRAG differ from vector RAG?**
   Vector RAG finds chunks whose embeddings are close to the query. GraphRAG
   finds entities and relationships by pattern matching and traversal. They
   answer different questions well: "what text is most related" versus
   "what connects to what."
8. **What is multi-hop retrieval, and why can vector search struggle with
   it?**
   Answering a question that requires chaining more than one relationship,
   for example an impact-analysis question across two or three hops. Vector
   search can only retrieve it if one chunk happens to state the whole
   chain; a graph traversal composes it from separate facts.
9. **How can graph and vector retrieval be combined?**
   By running both and merging results, for example appending graph facts
   after the ranked vector list (`vector_plus_graph`), or resolving query
   entities first and using their linked documents to reorder the vector
   results (`graph_seeded_vector`). Results are appended or reordered, not
   interleaved with a freshly invented score.
10. **How does a knowledge graph differ from a vector database?**
    A vector database answers nearest-neighbor similarity queries over
    chunks. A knowledge graph answers pattern-match and traversal queries
    over typed entities and relationships. The schema is implicit in the
    first and explicit in the second.
11. **How does a knowledge graph differ from an ontology?**
    A knowledge graph stores instance facts (this service depends on that
    database). An ontology describes the schema those facts conform to
    (what a service is, what depends-on means, class hierarchy). They
    compose: an ontology can validate or expand queries over a knowledge
    graph's data.
12. **What is entity resolution or canonicalization, and why avoid fuzzy
    matching for it?**
    Deciding that two different mentions name the same real-world entity.
    Fuzzy matching can merge genuinely distinct entities that happen to
    have similar names; a small, hand-curated alias table plus exact or
    normalized matching avoids that risk at the cost of needing the alias
    added by hand.
13. **What is graph provenance, and why does it matter?**
    Provenance records where a fact came from: the document, chunk,
    extraction method, and confidence. Without it, a graph fact is an
    unverifiable claim; with it, the fact can be traced back to the exact
    sentence that produced it.
14. **How is graph authorization enforced?**
    The same tenant/role rule document-level ACL uses, enforced twice: once
    as a Cypher `WHERE` predicate before rows leave the database, and again
    in Python on every returned row, since a text-level predicate on a
    dynamically generated query can never be proven complete on its own.
15. **What happens to graph consistency when a document is deleted or
    changed?**
    Re-ingesting a changed document deletes its prior facts before
    re-extracting. Removing a document deletes its facts too. The one gap:
    a checksum-based "unchanged" shortcut in ingestion runs before graph
    extraction, so a Neo4j-only data loss is not detected or repaired by a
    plain re-ingest.
16. **Why is unbounded traversal risky in production?**
    Its cost grows with the branching factor raised to the power of the
    depth. A query with no hop limit against a dense, highly connected
    graph can consume unbounded memory or time. Every traversal should have
    an explicit depth bound, a result limit, and a timeout.
17. **What is the difference between deterministic and LLM-generated
    Cypher, and why does the distinction matter for security?**
    Deterministic templates are hand-written and parameterized; their
    behavior is fully known in advance. LLM-generated Cypher is produced at
    request time and can only be checked after the fact: validated by text
    rules, executed in a read-only transaction, and re-checked for
    authorization on every returned row, since no text validator can be
    proven to catch every unsafe query.
18. **When does GraphRAG improve retrieval?**
    When the answer composes facts from more than one document and no
    single passage states the full chain, for example impact analysis or a
    multi-hop dependency question.
19. **When does GraphRAG add unnecessary complexity?**
    When the corpus has few cross-document relationships, or when the
    relationships that exist are already stated directly in the prose a
    vector search would retrieve anyway.
20. **How do enterprise AI systems typically use semantic graphs
    together?**
    A property graph for fast, concrete traversal over specific entities,
    paired with an ontology layer for schema reasoning, standardized
    vocabularies, and mapping between systems that model the same domain
    with different terms. Neither replaces the other.
